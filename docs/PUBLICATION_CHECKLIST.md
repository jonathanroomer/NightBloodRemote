# Pre-publication checklist

This checklist is deliberately a human gate. `make audit` can find known
patterns; it cannot decide whether a story, image, prompt, identifier or
licence reveals more than its owner intended.

## Current release rule

Do not add a remote, create a public repository, push, publish a release,
upload a build or submit to an app store until the owner has completed the
independent second security audit and explicitly authorised that specific
action.

## 1. Source and history

- [ ] Work from this history-free public snapshot, not the private repository.
- [ ] Confirm `git remote -v` is empty before the owner approves publication.
- [ ] Run `git log --format=fuller` and inspect every author/committer identity.
- [ ] Run `git status --short --ignored` and account for every untracked and
  ignored file.
- [ ] Inspect the full staged tree with `git diff --cached --stat` and
  `git diff --cached` before the first public push.
- [ ] Confirm there is no submodule, Git LFS pointer or nested archive that can
  bring private history back in.

## 2. Personal and device data

- [ ] Search for names, personal email addresses, phone numbers, postal
  addresses, usernames and social handles.
- [ ] Search for absolute macOS and Linux home-directory paths, host names,
  volume names, private IPs and local service URLs.
- [ ] Search for Apple team IDs, certificate names, device UDIDs, provisioning
  profile UUIDs and bundle IDs owned by an individual.
- [ ] Search for Codex/ChatGPT account, user, task, thread, project,
  environment and controller IDs—even if they are not credentials.
- [ ] Review every screenshot, image, audio file, video, log and fixture for
  visible or embedded metadata.
- [ ] Confirm the only intentional personal story is the approved README text:
  this is the creator's first open-source project and Marshmallow was named by
  his two-year-old son. It must not identify the child or add contact details.

## 3. Credentials and powerful access

- [ ] Run `make audit` and investigate every result manually.
- [ ] Search for API keys, OAuth client secrets, OAuth client IDs, tokens,
  cookies, pairing codes, private keys and signed URLs.
- [ ] Inspect Keychain service names and test fixtures for copied real values.
- [ ] Confirm `CODEX_OAUTH_CLIENT_ID`, `CODEX_PROJECT_ID` and
  `DEVELOPMENT_TEAM` are blank in tracked configuration.
- [ ] Confirm no WebView receives a credential, environment ID, task ID or raw
  App Server method passthrough.
- [ ] Confirm no listener is bound to a LAN interface and no insecure `ws://`
  endpoint is used beyond documented loopback development.

## 4. Files and build products

- [ ] Confirm there are no generated `.xcodeproj` files, `xcuserdata`, derived
  data, archives, `.ipa`, `.dSYM`, signing files or simulator containers.
- [ ] Confirm there are no `.blend` files, render frames, caches, sampled audio
  or review videos.
- [ ] Inspect the app icon with metadata tools after the final edit.
- [ ] Run `node scripts/strip-png-metadata.mjs <icon.png>` on any final PNG
  assets, then decode and visually compare the result.
- [ ] Run `npm ci`, TypeScript checking, the WebGL production build, XcodeGen,
  `make test-build`, Swift tests on a deliberately selected booted Simulator,
  and an unsigned Simulator build from a clean checkout.
- [ ] Verify the result launches and both faces render without an account.

## 5. Legal, naming and provenance

- [ ] Confirm every code and asset contributor can release their contribution
  under the MIT Licence.
- [ ] Review the Nightblood/Cosmere fan-project name and wording with the
  relevant trademark, copyright and fan-use guidance before public launch.
- [ ] Confirm no Brandon Sanderson prose, audiobook sample, character artwork
  or other third-party protected asset is included.
- [ ] Confirm the OpenAI/Codex and Anthropic/Claude acknowledgements describe
  collaboration without implying endorsement.
- [ ] Confirm the app icon, Blender scripts, shaders, prompts and procedural
  sounds are original or separately licensed, and record any exceptions.
- [ ] Choose a maintained private security-reporting route before launch.

## 6. GitHub settings after explicit approval

- [ ] Create the repository with no autogenerated README, licence or
  `.gitignore` that could conflict with this reviewed tree.
- [ ] Keep it private for a final server-side inspection if desired.
- [ ] Enable secret scanning, push protection, dependency alerts and private
  vulnerability reporting where available.
- [ ] Add branch protection after the initial reviewed import.
- [ ] Check the GitHub file list and commit author as rendered by GitHub before
  changing visibility.
- [ ] Only then, and only with explicit approval, make the repository public.

## Final sign-off

Record the commit hash, audit date, reviewer, test devices and any accepted
exceptions. A pass is specific to that exact commit; later changes require a
new review.
